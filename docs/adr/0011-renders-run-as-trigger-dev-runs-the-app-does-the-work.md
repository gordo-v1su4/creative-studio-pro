# Renders run as Trigger.dev runs, and the app does the provider's work

A confirmed render has to finish with the browser closed. Each one becomes a run on the operator's self-hosted Trigger.dev (`trigger.v1su4.dev`), in a project of its own, on a queue per render provider. The run only keeps time and order: it asks this app to send the render, waits, asks this app to check it, and stops when the app says it is done or has failed. This app prices, sends, checks, collects the file, records the take and stores it in Review Room, through one small set of addresses that accept the task's token and refuse a report that is out of date.

We chose this over two alternatives. A loop inside the app would have needed no second system, but the operator ruled it out: Trigger.dev already carries the queues, limits, run history and live progress for Pindeck, Stack Structure and Review Room, and a fifth hand-made queue would have none of that. Doing the provider's work inside the task, as Stack Structure does for its paid Higgsfield task, was the other choice. It was turned down because a task shares no files with this app: the still and the references a render reuses live in the project's own folder, the project is a versioned file with one writer, and "Get price" has to answer inside the app in any case. Putting send and check in the task would have meant two homes for each provider and every input copied over the network first.

**Consequences**: without Trigger.dev settings nothing can be confirmed, and the queue says so; there is no fallback loop. The app must be reachable from the task containers on the App VM, and the task's token is one more documented secret. A send is never retried by the run itself, so a provider cannot be paid twice; the app's send address answers a repeated call with the job it already started. A local test copy runs its tasks on the same machine with Trigger.dev's dev mode, so local renders never touch the hosted queue. The Higgsfield CLI and the fal.ai key live with the app, not in the task image. Live progress comes from Trigger.dev, but the project's own record of each render stays the truth: if the two disagree, the project wins.
